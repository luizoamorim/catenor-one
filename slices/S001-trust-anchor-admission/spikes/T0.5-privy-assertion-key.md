# T0.5 — Privy Credential Assertion Key spike

**Date:** 2026-09-10  
**Status:** **PASSED WITH APPROVED DESIGN AMENDMENT (maintainer, 2026-09-10; PLAN D1, D3, D33–D35).** Original spike verdict: STOP-GATE — PARTIAL PASS. Wallet provisioning, public-key derivation, plain Ed25519 signing and local verification, owner-authorization enforcement, and denial of transaction signing, raw signing and key export were **observed live**. The planned length guard (`signMessage` allowed only when `message.byte_length eq 64`) **does not work for binary messages**: Privy denied the authorized 64-byte binary message. Per PLAN §13.2 / TASKS T0.5 this is reported to the maintainer; no alternative signer, curve, suite or crypto profile has been chosen.  
**Spike decision under test (maintainer):** dedicated Privy **Solana** wallet (Ed25519) used only for credential/assertion signing, separate from any user EVM/account wallet, never a financial execution wallet. This is a Catenor key-purpose separation choice, not a protocol decision. The 64-byte message was a **spike constraint only**, not a Catenor Protocol requirement. Crypto profile (D3) and S001 semantics are unchanged.  
**Harness:** `scratch/privy-spike/run.mjs` (main) and `scratch/privy-spike/diagnose-length.mjs` (length diagnostic), git-ignored. Credentials came from the git-ignored `scratch/privy-spike/.env` and were read only by the scripts; the agent never read or printed them. Owner/authorization keys were ephemeral in-memory P-256 keys, one per wallet, never written anywhere. Outputs are sanitized (IDs truncated; no key material). Leak check over the outputs found no secret, key or full ID.

## 2. What was executed (Privy development app, synthetic data only)

- **Main run:** one policy `catenor-t0.5-assertion-key-spike` (Solana; rules: ALLOW `signMessage` when `message.byte_length eq "64"`; DENY `exportPrivateKey`; DENY `exportSeedPhrase`; owner = ephemeral P-256 key) and one Solana wallet owned by the same key with that policy attached. It then ran tests W1–W2, A1 and D1–D8.
- **Length diagnostic:** four more wallet+policy pairs (Privy allows one policy per wallet), each with an ALLOW `signMessage` rule: no condition; `byte_length eq "88"`; `byte_length eq "64"`; `byte_length lte "64"`. Each pair was probed with four messages: binary 64 B (SHA-256‖SHA-256, the shape of `eddsa-jcs-2022` hashData), 64 ASCII characters, 64 ASCII hex characters, and binary 32 B.
- **Not executed:** `signAndSendTransaction` and `transfer` (no-broadcast / no-funds rule), and any owner-authorized policy change.
- **Leftovers:** five synthetic, unfunded wallets and five policies remain in the dev app. Their owner keys were discarded, so they can no longer sign or be changed.

|---|---|---|---|
| F1 | Dedicated Solana wallet can be provisioned server-side with an owner and a policy | **CONFIRMED** | `chain_type: solana`, `owner_id` set, policy attached |
| F2 | Public key obtainable without export | **CONFIRMED** | the base58 `address` decodes to 32 bytes and verifies signatures as the Ed25519 public key; Multikey `z6Mk…` derived. The response has no `public_key` field; `exported_at: null` |
| F3 | `signMessage` signs the raw bytes with plain Ed25519 (no prefix, no hash) | **CONFIRMED** | every allowed signature is 64 bytes and verifies with `@noble/curves` over the raw message. It does not verify over the Solana off-chain-prefixed message or over SHA-256(message). Checked for binary 64 B, binary 32 B, ASCII 64 and hex 64 inputs |
| F4 | Policy can restrict `signMessage` to 64-byte messages (`byte_length eq "64"`) | **FAILED for binary messages** | authorized binary 64 B → `400 policy_violation` (main A1 and diagnostic). Binary 32 B is also denied under `lte "64"`, while 64 ASCII/hex characters are allowed under `eq "64"`. No input matches `eq "88"`, so the base64 length is not what is measured. **Inference** (not documented): `byte_length` is computed on the message decoded as text, which inflates non-UTF-8 binary input. The condition behaves as specified only for text messages |
| F5 | Owner authorization is enforced | **CONFIRMED** | `signMessage` without an owner signature → `401` "Missing `privy-authorization-signature` header"; policy removal without an owner signature → `401` |
| F6 | Messages outside the rule are denied | **CONFIRMED** (as a denial) | 32 B and 65 B binary → `400 policy_violation`. Given F4, this does not prove that length is being enforced |

Docs say that for sign-and-send, simulation runs before policy evaluation, so an unfunded or invalid transaction cannot show policy enforcement without breaking the no-funds rule. ## 4. Differences from our assumptions / PLAN §13

1. **`byte_length` is not a raw-byte length for binary messages** (F4). PLAN §13.1 policy `ALLOW signMessage when message.byte_length eq 64` over a binary `eddsa-jcs-2022` hashData cannot be enforced as written.
2. **Export DENY is revocable by the owner** (F12); PLAN §13.1 treats it as a hard guarantee.
3. **Send-denial is not demonstrable** under the no-funds rule (F8).
4. **`raw_sign` is unavailable for Solana wallets** (F9) — a capability limit, not a policy result.
5. Owner can be a P-256 public key directly (PLAN assumed a key quorum; both are documented). The response has no `public_key` field; the address is the key (F2). SDK string input to `signMessage` is treated as base64, so callers must pass bytes.

Unchanged and positively confirmed: plain Ed25519 over raw bytes (the core requirement of PLAN §13.2 item 1), default-deny for transaction signing, export denial while the owner key is held, and the server-side authorization flow (PLAN §13.2 item 3).

## 5. Proposed PLAN/TASKS changes — proposals only, NOT applied (maintainer decision)

Pick one way to handle F4. Options B and C touch the crypto profile (D3) and need explicit approval:

- **A. Drop the length condition.** Policy = ALLOW `signMessage` (no condition) + DENY exports; transactions, raw signing and send stay denied or unavailable. The 64-byte guard moves into the Catenor signer adapter (T5.2 already lists a "64-byte guard"). Weaker: Privy itself would sign any message for an authorized caller. Crypto profile unchanged.
- **B. Sign a text encoding of hashData** (e.g. 128 lowercase hex characters) with `byte_length eq "128"` or a `content` condition, and verify accordingly. This changes what is signed, so it is a crypto-profile change and breaks plain `eddsa-jcs-2022` compatibility unless separately specified. Not recommended without a profile review.
- **C. Ask Privy** whether `byte_length` on Solana `signMessage` is defined over decoded bytes, and whether a raw-byte length condition is planned.

For F12, add to PLAN §13.1 / §31 that export denial holds only while owner-key custody holds. Optionally adopt Privy's owner/additional-signer split: management key as owner, signing key as a policy-bound additional signer. This should be tested in a follow-up spike before relying on it.

For F8, record transaction-*sending* denial as a documented default-deny property that was not demonstrated live.

T0.5 stays **unchecked** until the maintainer decides.

## 6. Maintainer decision (2026-09-10) — T0.5 PASSED WITH APPROVED DESIGN AMENDMENT

- **Option A adopted; C pursued non-blocking.** Kept: dedicated Privy Solana wallet, Ed25519, raw-byte `signMessage`, current crypto-profile direction. The assertion payload is **not** changed to text to satisfy Privy.
- **Signer boundary (PLAN D33, §13.4):** structured inputs only → canonical message built inside the signer → exact format/length validated → Privy `signMessage` → independent Ed25519 verification. 64 bytes is the current profile value, not a protocol requirement.
- **Owner/signer separation (PLAN D34, §13.1.1):** management key = wallet owner (administrative only, not in the runtime); runtime key = additional signer scoped by the policy; runtime signer must not change owner/policies/signers or export (verified in T5.2).
- **Send transaction (PLAN D35):** signing denial CONFIRMED; sending denial UNCONFIRMED LIVE; default-deny documentation-supported only; not a Phase 0 blocker.
- **Privy question (PLAN Q6, TASKS T0.5q):** does `byte_length` intentionally operate on the decoded/textual message for Solana `signMessage`, and is there a raw-byte length predicate? Asked asynchronously; nothing waits on it.
- **Claim limit:** T0.5 proves a usable Ed25519 signing primitive whose signatures verify independently; it does **not** prove W3C `eddsa-jcs-2022` interoperability (tested in T2.3 / T5.2).
