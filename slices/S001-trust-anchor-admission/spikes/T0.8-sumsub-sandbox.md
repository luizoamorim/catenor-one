## 4. Proposed PLAN corrections (NOT applied — maintainer review)

1. **§20.2 row 1 / §20.4 linkage source.** Read beneficiaries from `fixedInfo.companyInfo.beneficiaries` and `info.companyInfo.beneficiaries`; record in the private trace which path supplied the linkage. Final rule after the live run shows where the API link appears.
2. **§20.2 row 3 / §17.5 budget.** Registry status is only documented on the checks endpoint → HTTP call #3 is likely **required**, not optional. Budget stays 4 of 5 (company, representative, company check, callback); headroom 1.
3. **§16.1 `activeRegistryStatuses` normalization.** `companyCheckInfo.status` is free-form with inconsistent casing. Proposal: compare after ASCII lowercase + trim against a configured allowlist (e.g. `["active"]`); anything else or absent → `false`/`MISSING` per D4. This is a Catenor evidence-acceptance parameter → maintainer decision.
4. **§16.1 `amlRejectLabels`.** Choose the set from S10 (proposal: all eight). Maintainer decision (policy-parameter semantics).
5. **§20.5 representative authority evidence class.** Proposal: state explicitly that in S001 (Sumsub sandbox, API-linked party, no Expert-assisted KYB) `REPRESENTATIVE_AUTHORITY_CONFIRMED` means *"operator-declared representative linkage recorded at the provider, with both company and representative reviews GREEN under the accepted levels"* — **not** provider-verified authority. Judge Inspector shows this limitation (already required by SPEC §12.2/D7); the evidence class string goes into the Bootstrap Configuration.
6. **§4.2 / binding-gate threat note.** `externalUserId` is mutable via API/dashboard. The binding gate proves the applicant carried the expected bindingRef at read time inside the TEE; it does not prove the value was never changed. Add this to PLAN §31 threats (holders of the Sumsub app token/dashboard could re-point a bindingRef).
7. **T4.4 bindingRef format.** Keep `[a-z0-9-]` (well under 512 chars) until the live run confirms the charset.
8. **Sandbox result forcing.** If `testCompleted` does not work on company applicants, use the documented sandbox verification presets (Approve/Reject per check, /docs/test-in-sandbox) or mock-company data; TV-L03 fixture DENY remains the fallback. Decide after the live run.

### Differences from documented assumptions (individual applicants)

1. **`testCompleted` needs no precondition for individuals** (docs listed none; observed): it succeeds directly from `init`, with no documents uploaded and no check requested. Sandbox results are therefore **entirely synthetic** — nothing about identity documents was checked. This reinforces the "Sumsub sandbox" labeling rule (D6) and must be stated in the Judge Inspector.
2. **Absent, not empty, on GREEN:** for GREEN, `reviewRejectType` and `rejectLabels` are **omitted** from `reviewResult` (not `null`, not `[]`). Consistent with the docs ("available if `reviewAnswer` returns `RED`"). Proposed normalizer rule: when `reviewStatus = completed ∧ reviewAnswer = GREEN`, an absent `rejectLabels` means "no labels" (not MISSING); in any other state an absent field stays MISSING (D4).
3. **`review.reprocessing: true`** after a simulated review (both GREEN and RED) — not in our assumptions or the docs we read. Not used by any fact rule; recorded only. Proposal: do not use it as a fact input; keep it out of the normalized preimage unless the maintainer decides otherwise.
4. **`reviewDate` appears only once completed** (absent at `init`), format `YYYY-MM-DD HH:MM:SS+0000` — matches the documented example; `EVIDENCE_FRESH` parsing can rely on this format. `review.createDate` shares the format.
5. **Review completion is immediate in sandbox** (completed at the first read; `elapsedSincePendingMs` < 1 s) — the demo does not need polling beyond one read.
6. **No company level exists in this sandbox** — confirms the KYB entitlement blocker. `ORGANIZATION_*` facts and `REPRESENTATIVE_AUTHORITY_CONFIRMED` cannot be observed yet.

No production semantics were changed; items 2–3 are proposals for the maintainer.
