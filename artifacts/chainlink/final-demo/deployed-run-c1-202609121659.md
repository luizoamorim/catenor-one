## 3. Findings for Chainlink (reported as observed)

1. **The gateway URL.** The docs page "Triggering Deployed Workflows" gives
   `https://01.enterprise-gateway.zone-a.cre.chain.link/` for the private registry. For this organization it answered
   `-32600 Workflow not found. 'workflowID' 0x… is not a valid workflow ID` for two ACTIVE private-registry
   workflows:
   - the confidential workflow;
   - a minimal non-TEE control workflow, `catenor-http-control` `0038de78…a66f`, deployed only to test this.

   `https://01.gateway.zone-a.cre.chain.link`, the only gateway URL embedded in CRE CLI v1.33.0, accepted the same
   signed request at once (HTTP 200, `ACCEPTED`). The demo now defaults to it; `DEMO_CRE_GATEWAY_URL` overrides.
   Three admission attempts failed on the documented URL before this was found. None created an execution, and the
   set-once root admission was not consumed.
2. **User logs are visible.** The simulator banner says user logs "will not be visible, and will not leave the TEE".
   On the deployed platform, the Logs tab shows the workflow's user logs from several DON nodes. The workflow logs
   only non-sensitive markers through `safe-log` (for example `secrets_fetched`, `offering_evaluated status=OK`,
   `handler_completed status=DELIVERED`), so nothing sensitive appears. Catenor makes no claim that logs stay in the
   enclave.
3. **Several callbacks per execution.** Each node's copy of an execution calls back. The relay keeps the first
   authenticated result per run and answers `409 LATE_OR_DUPLICATE_RESULT` to the others.
4. **Secrets.** `cre secrets create` parses `CRE_ETH_PRIVATE_KEY` from the `.env` it is given, even with
   `--secrets-auth browser`. The template's non-hex placeholder fails with `invalid hex character 'Y'`.
5. **Enrollment.** The first Confidential Workflow deploy on this account needed no extra step.
